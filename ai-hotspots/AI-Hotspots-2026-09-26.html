AI 热点综述 - 2026-09-26

2026-09-26 23:52 AI热点

AI 热点综述 · 2026-09-26

昨天讲的是账本——钱往哪流、谁在给谁买单。今天讲的是一件更尴尬的事：你怎么知道那些账单花得值。

Aaron Levie 说”你不能自动化你无法度量的东西”，Dan Shipper 让 Opus 5.5 解释”为什么个人基准很重要”，Thariq 则把已经被用麻了的 “effort” 拆开重算了一遍。三件事指的是同一个洞：agent 干了活，但大多数组织手里没有一把尺子。

与此同时，Guillermo Rauch 把”agent 能不能用你家产品”定义成了新的采购门槛，Amjad Masad 把业务分析的能力往每个普通人手里塞，Peter Steinberger 和 Thibault Sottiaux 各交了一次基础设施的学费。能力已经溢出了，接下来拼的是谁能把它稳稳接住。

一、evals 才是企业采用 AI 的闸门

Levie 今天这段几乎可以直接当内部备忘录发（195 赞、22 转发）：

你不能自动化你无法度量的东西。这意味着 evals 是 AI 在企业中扩散的闸门之一。

我们可以用软件测试确定性流程，但大多数企业没有任何有用的办法去理解他们那些非确定性流程今天跑得怎么样——尤其是 agent 替他们做的那部分工作。

对企业采用 AI 来说，evals 是任务关键级的，因为除此之外你没有别的办法知道什么在起作用、什么坏了、什么变了、什么变好了、什么可以多做。所有变更、升级和部署，都处在”有一套好 evals”的下游。

我们不仅会看到大量领域特定的 evals 在实验室和整个行业里涌现，每一家企业也都需要清楚知道 agent 在自己环境里表现如何。巨大的机会。

这段话真正的锋利处在最后一句的落点。 实验室会造 evals，但”agent 在你的环境里到底行不行”这件事，没有外部供应商能替你回答——它只能由你自己测量。这意味着 evals 不是采购项，而是组织能力项。

Dan Shipper 那条从另一个侧面给出了同样的结论（48 赞、2 转发）：

我让 Opus 5.5 解释为什么**个人基准（personal benchmarks）**如此重要（这是 one shot 出来的）

“个人基准”是个很少被认真对待的词。 公司有基准、榜单有基准，但一个具体的人——他做的活、他的代码库、他的判断标准——通常没有任何自己的度量。当每个人都能随手拉起一堆 agent 时，能不能给自己定义一把尺子，会变成个人层面的分水岭。

二、”对 agent 好不好用”正在成为新的采购门槛

Guillermo Rauch 今天把这件事讲成了三步（183 赞、14 转发）：

我们正在帮像 @klaviyo 这样的世界级组织构建 agentic 部署平台。

① 连接每一个 agent（claude、codex、cursor……）
② 通过他们的 IDP（Okta、Entra）配置 SSO
③ 现在每个人都可以安全地”开火”了®

当每家公司都这么搭起来之后，SaaS 会变成什么样？我经常被问这个问题 😁

首先，数据必须来自某处。这些应用只有能被注入业务数据才成立。这就是为什么我们看到大型企业 SaaS 厂商突然把发布 CLI 和 MCP 排在优先级前列，或者把被忽视多年的 API 重新翻出来。

新的”采购门槛”将是你的产品对 agent 有多好用，而不是对人。 它们能多容易地导航你的本体（ontology）并操作你的数据。

一旦这件事到位，我怀疑会有一长尾的 SaaS 应用再也不会被人买。它们会被生成出来。 而且更安全、更快、更现代、更贴合每家公司、每个员工的需求。

“采购门槛从人换成了 agent”是今天最有产业含义的一句。 过去二十年，SaaS 的设计目标是”让人类的点击路径更短”；Rauch 在说，接下来要比的是”让 agent 的调用路径更短“。而终局更狠——会有一批软件不是被买来的，是被当场造出来的。

配套那条像是给这句话作的注脚（331 赞、7 转发）：

npx skills 的增长简直离谱。我看着它从点子，到第一次发布，到出现在互联网每一个 README 上。

我们曾经写代码，现在我们写英语。

“写英语”是个漂亮的双关。 一方面它说的是自然语言成了新的接口；另一方面它暗示——文档本身变成了分发渠道。一个 README 里的 npx skills，就是一次对 agent 的招商。

而 Amjad Masad 从另一个角度补上了同一块拼图（242 赞、10 转发）：

我们思考了很久”自驾驶公司（self-driving company）“意味着什么。其中很大一部分，是把理解一门生意的能力，交到每个人手里。

Atta 构建了一种漂亮的业务分析与数据可视化方法，他们和我们一样相信，有用的智能应该对每个人都可用。

欢迎 Omar、Amine 和 Atta 团队加入 Replit！

“自驾驶公司”和”把理解生意的能力交到每个人手里”，与 Rauch 的”agent 采购门槛”是同一枚硬币。 一边是每个软件都要对 agent 开门，另一边是每个普通员工都要能直接向数据提问——夹在中间的翻译层（BI 工具、报表、数据分析师）正在被压缩掉。

三、那个不是普通 Slack bot 的同事

Boris Cherny 今天这条是全天最有画面感的一条（1096 赞、52 转发）：

Tag 每天写着我们 50% 以上的 PR。它还干了大约 100% 的数据分析，并修掉了我们大部分的产品反馈和 bug。

它不像一个普通的 Slack bot。它是主动的、可编程的，它有记忆，它能访问你的各种连接器。配上 Opus 5.5 和 Fable 5.1，它有很强的判断力。

我常用的示例提示词：

  • “@Claude 对这个频道里已解决的帖子用 ✅ 反应”
  • “@Claude 从现在开始，对频道里每个 bug 都尝试端到端复现，跑完整个 app。一旦复现成功，就提一个 PR 修掉它，并 tag 对口的团队来做 code review”
  • “@Claude 对’这个奇怪的数据到底怎么解释’头脑风暴大约 100 个假设，用 workflow 去验证/证伪。花掉大概 1000 万 token 往深里挖。把结果画成图。”
  • “@Claude 给我做一个交互式游戏，解释这部分代码是怎么工作的，然后做一份 slide deck 讲给团队里的其他人听”

真正的信号不是”50% 的 PR”，而是第二条提示词的结构。 注意它是什么形态：“从现在开始””对每个 bug””一旦复现就……”——这不是一次性指令，而是给一个常驻同事下的岗位职责。第一条 “@Claude 对已解决帖子点 ✅” 甚至都不算任务，而是在训练一个同事的工作习惯。

这也解释了为什么它必须”有记忆、能访问连接器、主动”。 一个无状态的 bot 只能被调用；一个有状态、有连接器、会自动观察的 agent 才能被授权。而授权的前提，正好接回第一部分——你敢把这条规则写进频道，是因为你有办法验证它执行得对不对。

四、”effort”：当”用多大力”变成一个可调参数

Thariq 今天花了一整天，把一件已经被用麻了的事拆开（3517 赞、260 转发）：

effort 到底是什么？什么时候该调它，为什么不干脆全部用 max effort？

我深挖了这个问题，去看了 evals，也自己做了测试，结果让我相当意外。

配套那条给出了他自己的用法（321 赞、23 转发）：

想保持自己在环里（in the loop）的时候，我更多用 effort low；只有在完全不想插手、或者想去找安全漏洞的时候，才基本用 effort max。

这条把”effort”从一个玄学旋钮，变成了一个关于”人要留在哪一环”的产品决策。 低 effort = 我盯着、我参与、我要频繁纠偏；高 effort = 我退场、我要它自己扛完。参数的名字叫 effort，真正被调的其实是”人的介入程度”。 他还顺手放了个交互式解释页（140 赞、6 转发），延续了昨天那种”把方法本身当内容发布“的分发习惯。

和第一部分放在一起看更有意思： Levie 说企业缺度量，Thariq 说”我去看了 evals，结果出乎意料”——连本行业内最前沿的人，对自己产品最重要的那个旋钮，直觉都可能是错的。 这正是 evals 存在的意义。

五、基础设施的债：从 sqlite 到 codex

Peter Steinberger 今天很坦诚地交代了一个设计错误（1043 赞、46 转发）：

把 OC 迁到 sqlite 时我犯的最大设计错误：用了同步的数据库访问。当它只是一个在 Slack 或 iMessage 里向你汇报的 agent 时，这没问题；但现在一个 agent 可能并行跑 50 个会话、整个团队都在上面工作，这就成了瓶颈。

我有一个和 Astra 的 /goal，到现在为止已经提交了 575 个 PR，把一切迁移到异步 worker 上。我们边推进边把这些改进发出去。连大规模重构都不再可怕了，这挺疯狂的。

“用一次重构提交 575 个 PR”本身就是今天最硬的数据点之一。 它说明的不只是”agent 能写代码”，而是重构这种过去要靠”熬”的工程活动，其经济性已经被改变了——当一次性大改的边际成本被拉低，”先上线、以后再还技术债”的诱惑会更强，同时也终于有能力真的把债还上。

而 Thibault Sottiaux 那边则是一场原汁原味的事故现场（12780 赞、671 转发）：

o yes…… 我们回来了，而且会为所有付费用户重置 codex 和 ChatGPT work 的用量限制。

抱歉刚才的短暂中断！

（以及是的，我们有一个专门的备用 codex，出事时来帮我们😂）

配着出事时的两句（10596 赞、574 转发：”我们注意到 codex 挂了，正在努力恢复”；2687 赞、44 转发：”o no :(“）。

1.2 万个赞说明的是一件挺残酷的事：整个行业的开发节奏，已经真实地压在少数几个服务上。 一次中断，就能让”重置付费用量限制”这种级别的补偿显得理所应当。分布式系统的冗余设计已经很成熟了，但在”模型供应商”这一层，大家其实是在共享同一个单点。
