今日热点

今天的 GitHub 榜单可以说是被 Agent Skills 一个词统治的：12 个上榜项目里，有 6 个直接是”技能包”或”技能基础设施”。但真正值得看的地方不在数量，而在形态的变化——skills 正在从”我复制粘贴的一段 prompt”，分裂成四种东西：打包格式（stitch-skills 对齐 Agent Skills 开放标准）、领域垂类（Claude-BugHunter 的 82 个安全技能、claude-trading-skills 的量化技能）、时效知识（modern-web-guidance-src 给 agent 喂”这个平台现在该怎么写”）、以及最关键的——质检（NVIDIA 的 SkillEvaluator）。当一个东西开始需要”质量门禁、语义重叠检测、合成评测集”，它就正式从玩具变成了供应链。

另一半的戏在”Agent 怎么被人用”这一层：plannotator 做人机共审的工作台（+860 星），ag-ui 定义了 Agent 与前端之间的交互协议，univer 把自己的文档引擎重新包装成”AI 办公 SDK”（+1,041 星）。加上阿里开源的混合式代码审查、腾讯的 coding agent SOP 编排器——今天的主线是 agent 落地的三个卡点：技能从哪来、人怎么插手、企业怎么审。

GitHub 热门 AI 项目

1. NVIDIA/SkillEvaluator —— 技能终于有质检了

Python · 1,329 stars · +133 today

这是今天最”不性感”但对生态最重要的一项。它的存在本身就是一份诊断书：skill 已经多到没人能判断哪个该装了。

NVIDIA 给的方案是多层评估框架，四个能力点值得逐条拆：

  • Quality Gates（质量门禁）。技能不是”能跑就行”，得有硬性门槛——描述是否能让模型正确路由到它、参数是否自洽、依赖是否可满足、触发条件是否与真实意图对得上。这是把软件工程的 CI 思维搬进 prompt 目录。
  • 语义重叠检测。这条最实用。装了 20 个 skill 之后最大的问题不是坏技能，而是两个技能都能接同一个请求，模型随机选一个，行为不可复现。重叠检测相当于给技能集做”去重与冲突分析”。
  • 合成评测数据集生成。没有测试集就谈不上评估，但没人愿意为每个 skill 手写用例。合成生成是唯一现实的路径——代价是评估本身的可靠性也要打折。
  • Live agent evaluation。最终还是要看”装了它之后 agent 的行为变了多少”。这一层最难，因为它要求有一个可重复的任务环境和行为度量，而不是看输出像不像。

我的判断：这类框架短期内不会好用，但方向绝对是它。 因为 skill 生态的核心风险不是”没有好技能”，是”技能库变成了一个没人敢动的黑箱”。你装了 50 个技能，其中 3 个在偷偷改你的构建脚本——这种事只要发生一次，团队就会把整套东西删掉。质检层是让这个生态能长大的前提。

2. google-labs-code/stitch-skills —— 技能要走开放标准

TypeScript · 9,065 stars · +248 today · 1,076 forks

Google Labs 出的技能库，配套 Stitch MCP server。它真正的卖点在描述里那句”每个 skill 都遵循 Agent Skills 开放标准，兼容 Antigravity、Gemini CLI、Claude Code、Cursor”。

这句话翻译一下：Google 在自己最不占优势的那一层选择了不竞争。 它没有搞一套自己的私有技能格式绑定自己的 CLI，而是对齐了一个跨厂商标准。对一个拥有 Gemini CLI、Antigravity 两条产品线的公司来说，这个选择挺有意思——它赌的是”技能的可移植性”比”技能格式的所有权”更值钱。

从工程角度看，stitch-skills 里最值得抄的是技能与 MCP server 的耦合方式。技能不直接调 API，而是声明”我需要哪个 MCP 工具、什么参数形状”，由宿主注入。这样同一份技能在 Claude Code 和 Gemini CLI 里跑，只是 MCP 连接不同，技能本体不用动。这是把”能力声明”和”能力实现”分开——和十多年前接口/实现分离是同一个道理，只不过这次的对象是工具调用。

3. GoogleChrome/modern-web-guidance-src —— 给 agent 补时效性

TypeScript · 6,728 stars · +1,220 today

今天涨幅第一。名字很朴素，做的事也不复杂：维护一份”当前 Web 最佳实践”的知识源，让你的 coding agent 别再用 2021 年的写法。

这个项目的存在揭示了一个很少被认真讨论的问题：模型的知识截止日期，是所有 agent 产品的隐形负债。 训练数据里 position: sticky 的兼容性坑、已被废弃的 document.write、React 18 到 19 之间那些破坏性变更——这些不是”模型不够聪明”，是它没见过。

所以”给 agent 喂最新最佳实践”这件事，本质上是把知识更新从模型侧挪到上下文侧。不改权重、不微调，直接在每个会话里注入一份可版本化的现状描述。代价是 token，收益是修 bug 的速度从”等下一代模型”缩短到”改一行 markdown”。

+1,220 这个数字说明很多人已经踩过这个坑了。

4. ChromeDevTools/chrome-devtools-mcp —— 56K 星的隐形基础设施

TypeScript · 56,646 stars · +718 today

榜单上星数最高的项目。一句话：把 Chrome DevTools 暴露成 MCP 工具，让 coding agent 能真正”看”浏览器。

为什么它重要？因为绝大多数 agent 的浏览器能力停留在”截图 + 点击坐标”这种脆弱的层面。而 DevTools 提供的是结构化的真相：控制台错误、网络请求瀑布、DOM 树、Performance trace、内存快照。有了这些，agent 修前端 bug 的路径就从”猜—改—再看截图”变成了”读错误栈—定位文件—改—验证请求成功”。

它的星数增长曲线也说明一件事：在 agent 时代，”能被程序调用的调试器”比”更聪明的模型”更稀缺。

5. dream-num/univer —— 把文档引擎重新包装成 AI 办公 SDK

TypeScript · 25,264 stars · +1,041 today

Univer 原本是一个开源的在线表格/文档套件（对标 Google Sheets 那类）。今天的定位变了，一句话写得很清楚：“Build your own AI office with Univer Office SDK … for people and AI agents.”

这个转向值得注意。传统 office 套件的 API 是给人用的：菜单、快捷键、选区。而 agent 需要的是另一套东西——把”表格”抽象成可寻址的数据结构，让模型能读单元格范围、写公式、做批量格式化，并且每一步可回滚。这中间的差距不是加个聊天框能填平的。

Univer 的做法是把编辑、计算、协作、文件处理四件事拆成独立能力，通过 SDK 暴露。对想做”垂直行业 AI 办公”的团队来说，这比自己从零写一个电子表格引擎现实得多——公式引擎和协同 OT/CRDT 这两块，是那种”看起来简单、做起来两年”的东西。

6. ag-ui-protocol/ag-ui —— Agent 与前端的交互协议

TypeScript · 17,590 stars · +393 today

AG-UI 想解决的是个很具体的问题：agent 在后台跑，前端怎么把过程演出来？

今天的常态是每个团队自己造一套 SSE 事件格式——thinking、tool_call、tool_result、message_delta ……各写各的，换个前端框架就得重写一遍。AG-UI 把这件事标准化：把 agent 生命周期定义成一组事件流，前端按事件渲染，后端按事件发。

和 MCP（agent 调工具）、A2A（agent 调 agent）放在一起看，这张拼图就完整了：MCP 是向下接工具，A2A 是横向接同类，AG-UI 是向上接人。 三个协议各管一个方向，缺一个 agent 系统就不闭环。

7. backnotprop/plannotator —— 人机共审的工作台

TypeScript · 11,613 stars · +860 today

昨天它就在榜上，今天继续涨 860。定位是一句话：”stay in the loop and on top of agents”。具体形态是一个工作台：shaping（先谈清楚要什么）、decide（拍板）、plan（看它的计划）、annotate（在代码/文档上批注）、review（审 diff）、share（发给同事）、一键把反馈送回 agent。

这类产品的价值不在功能列表，在于它承认了一个事实：agent 不需要”更多自主”，它需要”更好的中断点”。

一个能跑 40 分钟的 agent，如果只在最后给你一个 diff，中间 39 分钟就是黑箱。而如果它每 5 分钟停下来问一次”这里我理解得对吗”，体验就变成了电话会议——更烦。真正好用的是异步的、结构化的、不打断执行的旁路：agent 继续跑，你在旁边把意见攒着，攒够了在关键节点一次性回灌。plannotator 做的就是这个旁路。

8. alibaba/open-code-review —— 确定性与概率性的混合

阿里开源 · 支持 OpenAI / Anthropic 兼容接口

阿里的代码审查工具，技术上最有意思的是它明确宣传自己是混合架构：

  • 确定性流水线：规则引擎先跑一遍，覆盖 NPE、线程安全、XSS、SQL 注入这类有明确正确答案的问题，多语言规则集内置。这部分不能交给模型——漏报一次 SQL 注入，代价是事故。
  • LLM Agent：负责语义层的东西——命名是否误导、逻辑分支是否漏了边界、这段改动是否与 PR 描述对不上。这部分规则写不出来，只能靠模型。
  • 行级精确注释：把两类结果对齐到同一套行号坐标系里，输出到 PR。

这个架构值得单独抽出来讲，因为它回答了一个企业落地时最常问的问题：“AI 审代码靠不靠谱？” 正确答案是”看你让它审什么”。

注意最后那条虚线：驳回的结果应该回流。如果被驳回的意见不进入评测集，这套系统三个月后还是会在同一种误报上反复打扰人——然后被关掉。

9. Tencent/LoopForge —— 继续把 agent 关进 SOP

Go · 1,206 stars · +484 today

昨天分析过，今天继续涨 484，说明需求是真的。补充一个观察：这类”agent 编排 + 人工审批门”的项目，核心竞争点从来不是编排能力（画个 DAG 谁都会），而是状态与可恢复性——从任意节点重跑、把工作打回指定步骤、暂停/恢复/接管。一个不能回退的流水线，出问题时唯一的选择是全部重来，而这在生产环境里等于不可用。

技术洞见

洞见一：Skill 正在形成一条完整的供应链

把今天六个技能相关项目按”环节”排一下，会发现它们各自站在链条的不同位置：

这条链上，生产和分发已经很热闹，治理几乎空白。而历史经验是：任何一个生态，在治理缺位时都会经历一次”信任崩塌”，然后才长出规范（npm 的 left-pad、WordPress 插件市场、VS Code 扩展商店都走过这条路）。

所以给正在搭企业 agent 平台的团队一个具体建议：现在就该建自己的技能准入清单，哪怕只是一张表——技能名、来源、依赖、最后验证日期、谁负责。等到技能数过百再补，成本会高一个数量级。

洞见二：Agent 产品的竞争，正在从”能力”转向”接口密度”

今天榜上的 univer（办公 SDK）、ag-ui（前端协议）、plannotator（审阅工作台）、chrome-devtools-mcp（调试接口）、open-code-review（行级注释输出）——放在一起看，它们和”模型更强”没有半点关系，全都在解决同一件事：agent 的能力怎么进入已有的工作流。

一个能力再强的 agent，如果只能待在终端里，它的用户就是那批本来就在终端里的人。而要进入设计评审、客服工单、代码审查、办公文档这些场景，需要的是结构化的事件、可寻址的对象、可中断的流程——也就是接口。

这也解释了为什么 chrome-devtools-mcp 能拿 56K 星，而很多”更聪明的 agent 框架”只有几千星：能被程序调用的能力，比聪明本身更容易被集成。

对个人开发者的启示更直接一点：如果你在挑技术方向，“给 agent 做接口”的确定性高于”给 agent 做大脑”。大脑那一层只有少数几家能玩，接口那一层每一行代码都在产生复利。
